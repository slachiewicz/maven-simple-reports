= Maven Pull Requests & Branches Dashboard (SPA)
:icons: font

A statically hosted single-page app with two tabs covering the ~98 `apache/maven-*` repositories:

* *Pull requests* — every open PR (not just Dependabot's), with author, assignee and live build status.
* *Branches* — stale-branch detection: branches with no recent commits, no open PR, and no protection rule.

Both tabs call the GitHub GraphQL API directly from the browser, which rejects unauthenticated requests, so both require a token.

It replaces the previously cron-generated `dependabot-prs.html` page.

== Status

Two authentication paths are available:

. *Sign in with GitHub* — full OAuth Authorization Code + PKCE flow via a registered GitHub App.
Access tokens (~8 h) are refreshed automatically using the long-lived refresh token (~6 months).
. *Personal Access Token* — manually pasted into the Settings panel.
No expiry-handling, but works without any backend.

One of the two is *required*: every request the dashboard makes goes to GitHub's GraphQL API, which rejects unauthenticated requests outright.
Without credentials both tabs render a sign-in prompt and the app issues no request at all.

Either path draws on the same 5 000 points/h budget, which one repo's pull-request query costs ~1-2 points against.

== Architecture

* *Static SPA* built with Vite + React + TypeScript, deployed to GitHub Pages under `dependabot-prs/`.
* *Three small Netlify Functions* (`netlify/functions/`) act as the only server-side component, exclusively for the OAuth token exchange and refresh.
The functions never touch the dashboard's PR data — that still goes browser-to-GitHub directly.
* *Direct GraphQL calls* to `api.github.com/graphql` — no backend, no proxy. `lib/githubGraphql.ts` is the only client.
* *Serial request scheduling* (one in-flight request at a time) to stay within GitHub's secondary rate-limit guidance.
* *Backoff on 403/429* using `Retry-After`, and on a `RATE_LIMITED` entry in a 200 response's `errors` array.
* *Two independent polling loops* (`lib/useSweep.ts`, shared by both tabs) — only the active tab's loop runs; the inactive tab costs nothing until switched to.
** *Pull requests*: fixed 5-minute cycle. One query per repo returns the open PRs with their build-status rollup and assignees together, so a row paints complete rather than filling in over later phases.
** *Branches*: fixed 10-minute cycle.

== UI controls

Tabs::
Two tabs, *Pull requests* (default) and *Branches*, selected via a query parameter: `?view=branches` for the Branches tab, no parameter (or `?view=prs`) for Pull requests.
Only the active tab's sweep loop runs; switching tabs doesn't lose the other tab's data — results are persisted in `localStorage` and rehydrate instantly on return.
Browser back/forward moves between tabs by re-reading the URL.

Author filter (Pull requests tab)::
Three buttons — *All* (default), *Dependabot*, *People* — filter the PR table by author, with a live count on each button.
Classification trusts the GitHub API's `user.type` field for bots and pattern-matches Dependabot's login; anything else is *People*.

Stale-only / threshold (Branches tab)::
A *Stale only* checkbox, checked by default, restricts the branch table to stale branches. The age threshold defaults to *90 days* and is editable inline (1-3650); both settings persist in `localStorage`.

Settings · Sign in with GitHub::
The recommended path.
A *Connect with GitHub* button starts the OAuth Authorization Code + PKCE flow against a registered GitHub App.
The user is redirected to `github.com`, authorizes, and returns to the SPA with a fresh access token plus a refresh token.
Subsequent fetch cycles use the access token; when it expires (~8 h), the SPA quietly refreshes via the Netlify `token-refresh` function and continues without re-prompting.
The refresh token is valid for ~6 months.
+
The button only appears when `VITE_GITHUB_CLIENT_ID` is set at build time (see _Configuration_).

Settings · GitHub PAT::
The fallback path for environments without OAuth set up (no Netlify functions, or no Client ID in the build).
A Personal Access Token (fine-grained or classic, *no scopes required* for read-only public-repo access) can be pasted directly.
The settings panel links to GitHub's PAT creation pages so the token can be generated without leaving context.
The token is sent as `Authorization: Bearer …` on every request.
Adding or clearing a token wakes a paused cycle, so the new limit takes effect immediately.

Both auth paths::
A *Remember on this device* checkbox controls where the token (PAT _or_ OAuth) is kept: unchecked (default) stores in `sessionStorage` and is dropped when the tab closes; checked moves it to `localStorage` so it survives browser restarts.
+
[WARNING]
====
Both storages hold the token in plain text and expose it to any script running on this origin (XSS).
Only enter/connect on machines you trust.
Revoke the token on GitHub if the browser profile is shared.
The Netlify functions keep the GitHub App *client secret* server-side; only the short-lived user-to-server access token and refresh token live in the browser.
====

Repo filter::
A regex input narrows the fetch cycle to a subset of `apache/maven-*` repos.
The pattern is persisted in `localStorage` and applied immediately: previously fetched repos that no longer match are hidden, newly matching repos are queued for the next fetch.
Useful for keeping a cycle short when you only care about a few repos (e.g. `mvnd|surefire`).

Refresh now::
Re-queues all active repos in the current tab for an immediate refresh and lifts any pending rate-limit backoff.
The action is non-destructive: previously fetched entries remain visible until each repo is updated in place.

== Rate limits (important)

GitHub's GraphQL budget is *point-based*: 5 000 points per hour per token, where a point is roughly one hundred nodes a query could return rather than one request.
Both tabs draw on that single budget through one shared serial queue (`apiQueue` in `lib/githubFetch.ts`), so a rate-limit backoff triggered by either tab pauses both.

Measured cost per full cycle over ~98 repos:

* *Pull requests*: ~1-2 points per repo, so ~100-200 points per 5-minute cycle.
* *Branches*: ~3-6 points per repo, so ~300-600 points per 10-minute cycle.

Each repo's last successful result is persisted in `localStorage`, so a reload paints immediately from cache and then refreshes in place.
The UI surfaces the remaining budget and any pause state.

== Branches

The *Branches* tab (`views/BranchesView.tsx`) surfaces candidates for deletion: branches with no recent activity, no open PR, and no protection rule.

* *One query per repo* fetches up to 100 branch refs (`refs(refPrefix:"refs/heads/", first:100)`), each with its last commit, author, open-PR count, protection status, and ahead/behind counts against the default branch, in a single round trip.
* *Cost*: each query costs roughly 3-6 GraphQL points against GitHub's 5 000 points/h budget, so the fixed 10-minute sweep cadence leaves comfortable headroom across ~98 repos.
* *Exclusions* — a branch is never flagged stale if it is:
. the repository's default branch,
. protected (detected via `refUpdateRule`, the signal visible without repo-admin access — `branchProtectionRule` needs admin and would be null for every `apache/*` repo), or
. the head of an open pull request.
* If the ahead/behind comparison times out (it's evaluated per ref, and a full 100-ref page can push the query past GitHub's limit), the query is retried without it; the branch still appears with age and PR status, and a degraded notice is shown instead.

== Local development

[source,bash]
----
cd web
npm install
npm run dev          # http://localhost:5173/
----

== Production build

[source,bash]
----
npm run build        # outputs to web/dist/
npm run typecheck    # tsc -b --noEmit
----

The repo's top-level `scripts/generate_report.sh` runs `npm ci && npm run build` and copies `web/dist/` into `public/dependabot-prs/` so the existing GitHub Pages / Netlify deploy step picks it up.

== Tests

[source,bash]
----
npm test             # vitest run
npm run test:watch   # same, in watch mode
----

`npm test` runs Vitest over pure logic in `src/lib/*.test.ts` (author classification, the stale-branch predicate, build-status derivation, the GraphQL client's error handling, and similar). Components, network behaviour, and the `useSweep` polling loop are not covered by automated tests.

== Configuration

=== Asset base path

Asset URLs are emitted relative (`base: './'` in `vite.config.ts`), so the same build works at any deployment path: GH Pages under `/maven-simple-reports/dependabot-prs/`, Netlify branch deploys under `/dependabot-prs/`, or a local preview at the root.
Override with `PUBLIC_BASE=/foo/ npm run build` if you need an absolute base.

=== OAuth (optional)

Two Vite build-time variables enable the *Connect with GitHub* button:

`VITE_GITHUB_CLIENT_ID`::
Client ID of the registered GitHub App.
Publicly visible (it's in the OAuth authorize URL), so safe to commit per environment if needed; in this repo it's expected from the build environment instead.

`VITE_AUTH_ENDPOINT`::
Base URL of the Netlify Functions site that hosts `auth-callback`, `token-exchange`, and `token-refresh`.
Defaults to `https://maven-simple-reports.netlify.app`.

For local development, create `web/.env.local` (ignored by Git):

[source]
----
VITE_GITHUB_CLIENT_ID=Iv23xxxxxxxxxxxxxxxx
----

When the variable is unset, the OAuth button is shown disabled with a tooltip and a personal access token is the only way in.

=== GitHub App setup (one-time, admin only)

The dashboard authenticates against a registered GitHub App.
Steps to set one up:

. Register at https://github.com/settings/apps/new with:
+
* *Homepage URL*: the production SPA URL.
* *Callback URL*: `https://<netlify-site>.netlify.app/.netlify/functions/auth-callback` — exactly one URL covers every SPA origin, because the `auth-callback` function decodes the SPA's original origin from the `state` parameter and issues a 302 redirect back to the browser.
* *Webhook → Active*: off.
* *Permissions*: leave all empty (the higher rate limit applies without any scopes).
* *Where can this GitHub App be installed?* Any account.
* *Expire user authorization tokens*: on (provides the `refresh_token`).
* *Request user authorization (OAuth) during installation*: off.
* *Enable Device Flow*: off.

. After saving, copy the Client ID and generate a Client Secret.

. In Netlify, set two environment variables on the site that hosts the functions:
+
* `GITHUB_CLIENT_ID` — public.
* `GITHUB_CLIENT_SECRET` — mark "Contains secret values", so it isn't readable in the UI.

. Set `VITE_GITHUB_CLIENT_ID` in the SPA build environment (Netlify SPA site, GitHub Pages CI, or local `.env.local`).

=== Origin allowlist

Both the function CORS layer and the `auth-callback` redirect destination are gated by a small regex allowlist in `netlify/functions/_lib/cors.mts`.
Adjust it when adding new SPA deploy origins — for example, additional Netlify sites or custom domains.

== Known limitations

* A token is mandatory: there is no read-only anonymous mode, so the published page shows a sign-in prompt to a first-time visitor rather than data.
* Access and refresh tokens live in `localStorage` or `sessionStorage` (user choice) — accessible to any script on this origin via XSS.
A future hardening would move tokens into HTTP-only cookies set by the token-exchange function, requiring credentialed CORS.
* Merge-conflict detection is not implemented (`pullRequest.mergeable` is computed asynchronously by GitHub and returns `UNKNOWN` until it settles).
* Only the first 100 branches and first 100 open PRs per repo are fetched — neither paginates. A repo with more than 100 branches shows a "showing the first 100 of _N_" marker in the Branches tab; PRs have no equivalent truncation indicator.
* No build status is fetched for branches, only for PRs.
* Branch ahead/behind counts can be missing (shown as `—`) when the comparison query times out; see _Branches_ above.
* No service worker / push notifications.

== Why GraphQL only

The dashboard used to have a second, REST-based pull-request path so that visitors without a token saw something.
It was removed: it needed one inventory call per repo plus two enrichment calls per PR, which exhausted the anonymous 60 req/h budget on the first cycle, and it had to reconstruct by hand the rollup that GraphQL's `statusCheckRollup` returns natively — including the legacy commit statuses Apache Jenkins publishes, which never appear as check-runs.

`pullRequest.commits.last.commit.statusCheckRollup` returns both CheckRun and StatusContext entries in one field, and one query per repo carries the rollup, draft flag, base ref, title, author and assignees together.
The cost is ~1-2 points per repo against 5 000 points/h, versus roughly 1 170 REST requests for the same data across ~98 repos.

The trade is explicit: the published page is no longer viewable without signing in.
